# Magic 兑换码

## 操作入口

- 后台「积分与支付 → 兑换码」，路径 `/redemption-codes`。
- 支持每码 1–1,000,000 整数积分，单次 1–1,000 个，选填到期时间及备注。
- 生成结果可复制或下载；完整码只返回一次，数据库仅保存 SHA-256 和尾号。
- 生成请求带批次 UUID，重复提交不会再次生成。生成响应丢失时可在后台核对批次并停用未分发的码，再重新生成。
- 状态：未使用、到账处理中、已兑换、已停用、已过期；处理中的码不能停用。
- 用户「充值」页 `/billing/recharge` 输入兑换码；流水显示「兑换码赠送」。

## 记账规则与边界

- 兑换增加总余额、`gift_balance`、`total_gifted`，不增加 `total_recharged`。
- 额度为现有系统的整数积分，不是人民币；上游金额沿用站点积分兑换比例。
- 本站图片任务优先扣赠送，失败退款按原流水 `gift_amount` 恢复。人工扣减也优先扣赠送。
- 新字段从 0 开始，不猜测或重新分类历史充值、签到和其他赠送来源。
- 上游 sub2api 仍是统一余额；赠送分类只存在于 Magic 账本。直接发生在上游的其他消费没有独立赠送/充值来源，当前不能据此精确维护本地赠送剩余明细。累计兑换赠送和兑换流水不受影响。余额 API 对赠送显示做总余额上限保护，但这不等价于上游消费来源对账。
- 为避免把个人兑换额度误存到他人团队钱包，用户应切换到自己拥有的钱包后兑换。

## 并发与失败重试

- 先行锁定兑换码，持久化兑换人及上游目标 ID、URL、金额，再发起上游充值。
- 上游固定幂等键 `image2-redeem:{code_id}`；同一用户重复提交返回原结果，不重复记本地流水。
- 上游超时保留 processing，只能由原兑换人重试；不释放给其他用户。不要手工将 processing 改回 unused。
- 本地用户到账和兑换完成状态在同一事务提交，流水具有唯一幂等键。
- 上游重试安全依赖现有 sub2api 余额接口兑现幂等键契约；本地测试模拟了响应丢失，未对线上钱包进行实际充值测试。
- 按站点隔离，后台仅超级管理员、运营、财务可管理；用户兑换沿用现有限流机制。

## 发布

发布范围为 admin-server、user-server、admin-web、user-web。

先执行 admin-server 的 `alembic upgrade head`，再启动新版应用。新增迁移：

- `20260924_0100`：上游密码字段扩为 Text（前一项注册密码同步需求）。
- `20260924_0200`：兑换批次、兑换码表，账户赠送字段，流水赠送金额字段。

新密码加密使用现有 JWT 配置密钥派生的独立用途密钥。更换该密钥必须迁移已加密凭据；旧版本不会解密新凭据，不能直接回滚为旧应用版本。数据库迁移已在独立 PostgreSQL 测试库验证。

## 验证

- PostgreSQL 集成测试：并发抢兑、同用户并发重试、站点隔离、停用/过期、上游响应丢失重试、固定钱包目标、赠送消费退款。
- 后台测试：单批生成、哈希存储、分页、角色权限、匿名拒绝、重复批次、停用、迁移默认值。
- 两个前端生产构建；浏览器用模拟 API 验证批量生成、停用、兑换错误与成功，以及桌面/手机布局。

发布排空：在 user-web 容器内创建 `/var/run/image2-deploy-drain` 会暂时拒绝新的图片单个/批量任务提交（503），现有任务与状态查询不受影响。等待数据库 queued/running 归零后更新 user-server，再删除此标记恢复提交。
